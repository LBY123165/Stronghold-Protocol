# DEV-20261019-02 · 20 人容量层移植到上游 v0.3.1

## 基本信息

- 日期：2026-10-19，Asia/Shanghai。
- 分支：`capacity-0.3.1`（基线 `v0.3.1` = `b3deebda`）。
- 状态：**引擎与房间层已跑通**（分组卡池、并行选卡、领袖血池、房间容量、座位/容量 UI）；客户端的分组标签 UI 与容量测试仍在补齐。
- 关联：[DEV-20261019-01](2026-10-19-01-three-way-rebuild.md)（v0.2.4 基线的三合一）。

## 为什么要再做一次

DEV-20261019-01 交付的是「上游 v0.2.4 + 容量层 + 融合版皮肤/后台/部署」的可用整合版，但它落后上游 0.2.5 / 0.2.6 / 0.3.x。本次按「以最新上游为基座、只移植 20 人容量」重做一遍，取舍依据见 DEV-20261019-01 的「与 0.3.1 的关系」一节：上游 0.3.0/0.3.1 的主功能是插件系统，它**没有**容量、大厅匹配、局内聊天、公告、`/admin`、预缓存、紧凑协议、带宽应急；它的皮肤与素材管线是另一套实现。

## 范围

移植**只有容量**，以下一并不带（它们在龙千尘分支里与容量耦合，但属于另一条产品线）：

- 联机大厅 / 快速匹配 / 房主转让 / 匹配开关（`lobby.*`、`lobbyDiscovery`）
- 局内文字聊天（`matchChat`、`room.chat`）
- 公告（`announcements`、`announcementNotices`）
- 客户端预缓存与本地素材包（`assetCache`、`packs`）、带宽应急与冻结调度器（`bandwidthEmergency`、`freezeScheduler`）
- 紧凑 WebSocket 协议（`wireCodec`）
- `/admin` 运维后台与 Linux 部署脚本

## 怎么做的

容量层相对 0.2.6 基线是 **43 个文件、+1756 / −486 行**；其中 37 个文件上游 0.2.6→0.3.1 也改过，因此用三方套用（`git diff 488db49f <容量分支> -- <文件> | git apply --3way`）再逐个解决冲突。

| 层 | 文件 | 做法 |
|---|---|---|
| 基础 | `shared/playerCapacity.js`、`shared/constants.js`、`shared/protocol.js` | 直接取；`MAX_SEATS 4→20`、`BASE_SEATS/DEFAULT_SEATS/ROOM_CAPACITIES`、`room.create.capacity`、`room.setCapacity` |
| 卡池与选卡 | `pool.js`（`createPoolGroups`）、`choices.js`（`generateGroupDrafts`）、`spDraft.js`、`phases.js`、`unitePhase.js`、`unite.js` | 三方合并；`SharedItemPool` 同时保留 0.3.1 的 `debt` 与容量的 `scale`；`rollItemId/rollPool` 增加 `player` 并保留 0.3.1 的 `exclude` |
| 对局与结算 | `Match.js`（`poolGroups`/`playerPools`/`itemPoolFor`）、`infra.js`（`poolFor`）、`player/basics.js`（`ps.pool`）、`gamedata`/`finalAssault`/`bossRounds`/`settle`/`views`/`invariants`/`audit`/`bot`/`acquire`/`economy`/`prep`/`effectsMeta`/`platform`/`setupVote`/`clientCombat`/`StubMatch` 等 | 三方合并；0.3.1 的 offers/插件钩子保留 |
| 房间 | `server/lobby.js` | **不用机器合并**（那 13 处冲突混着 discovery/chat/assetCache/emergency，裁 80 处风险过高）：回到 v0.3.1 原版，外科式加 5 处——`capacity` 字段、按容量开座位、`create` 校验、`setCapacity` 方法、`toState().capacity` |
| 协议 | `shared/protocol.js` | `room.create` 接受 `capacity`（仅 4/8/10/16/20）、新增 `room.setCapacity` |
| 客户端 | `screens/lobby.js`（建房「同盟席位」选择器）、`screens/room.js`（`CapacityPicker`，来自干净补丁） | 外科式/直接保留；游戏屏、机变面板、队伍面板回到 v0.3.1 |

**API 适配**：容量层用 `sched.gameNow()`，0.3.1 的调度器只有 `now()` → 统一改 `now()`（`spDraft`、`phases`、`clientCombat`、`setupVote` 共 5 处）。

## 皮肤（P7）

- **能用的方式（已采用）**：`tools/skins-inject.mjs --from=<融合版 assets.json>` 把 172 干员 / 271 款写进 `data/assets.json`（271 款中 172 款带 Spine 战场模型）。v0.3.1 客户端就是从安装清单读 `chars[].skins` 的，因此皮肤直接可用。
- **插件方式（已做工具，未采用为默认）**：`tools/skins-plugin.mjs` 把已安装素材打成 cosmetic 插件（`--mode avatars` 16.1 MB / `--mode models|full` 按 `--limit-mb` 分卷），文件落盘名会转义 `@`/`#`。
- **上游阻塞**：`tools/plugin.mjs check` 对 `chars[].skins` 的 `name`/`group` 报 `PLUGIN_ASSET_FILE`（把展示名当成素材路径），而 `schemas/overlay.schema.json` 明确允许这两个字段。即 0.3.1 的 `readAssetOverlay` 与自己的 schema 不一致，**任何带名字的自建皮肤插件都过不了校验**。修法二选一：上游修 reader，或插件只写 `ref` + 素材、名字仍由安装清单提供。
- 生成的插件目录已加入 `.gitignore`（美术不进 git，与 AGENTS.md 的硬规则一致）。

## 已知缺口

1. **分组标签 UI**：容量层的机变面板会按固定组显示各自六张卡与「本组已完成」；本树仍用 0.3.1 的单页机变面板。服务端已按玩家所在组发卡，功能可用但同屏看不到别组进度。
2. **CSS**：`room-capacity`、`capacity-select` 等类名没有随行样式（容量选择器能用，样式朴素）。
3. **i18n**：新界面文字（`同盟席位`、`人数上限` 等）尚未加入 `public/i18n/` 五个语言包，`node tools/i18n.mjs check --all --strict` 会报缺项。
4. **容量专项用例**：龙千尘分支的 `lobby-capacity`/`player-capacity`/`draft-capacity`/`group-unite-rounds`/`feedback3-gift` 尚未移植；现有覆盖来自 0.3.1 原有用例 + 上述改写。
5. **`/admin`、公告、大厅、预缓存**：不在本分支（仍在 `alliance` 分支的 0.2.4 整合版里）。
